# Robot Arm Server — WebSocket API Reference

Internal engineering reference for every command the Node.js server (`server.js` + `servoWorker.js` + `kinematicsService.js`) accepts, and how much the Electron app (`electron-app/`) actually uses each one. Generated by auditing the source directly (not the older `API_DOCUMENTATION.md`, which predates several commands and has a few stale details — see [Appendix C](#appendix-c--gaps-vs-api_documentationmd)).

For the wire protocol basics (connection, JSON message envelope, response types) see `API_DOCUMENTATION.md` — this document assumes that and focuses on the full command surface plus internal call-site accounting.

## How to read the call-count columns

- **electron-app wrapper** — the `robotArmClient.js` method that sends this command, if one exists. Many commands are sent with the wrapper's own name; where the wrapper sends a *different* raw command string than its name suggests, that's called out.
- **Call sites** — the number of distinct places in the Electron app's source that invoke the wrapper (or send the raw command directly). This counts source locations, not runtime frequency. `blocklyRobotArm.js` sites are inside code-generator template strings (i.e., calls that end up in *user-authored* Blockly/RAPID/G-code programs, not the built-in UI).
- **Dead** — wrapper exists but is never called anywhere in `electron-app/`. Either legacy, or reachable only by external API clients (Python/C#/C++ examples).

## Command classification

| Class | Meaning |
|---|---|
| **Instant** | Answered in `server.js`'s main thread, no servo-bus access, no control session required. |
| **Bus-write** | Forwarded to the `servoWorker.js` child process; **requires holding the control session** (`takeControl` first) — rejected with `controlRequired:true` otherwise. |
| **Immediate** | A bus-write command that bypasses the normal write queue and runs on the bus right away (`moveJoint`, `stopJoint`, `stopAll`, `stopAllJoints`). |

⚠️ **Undocumented gap found in the code itself:** six read-only tool telemetry commands (`toolGetIdentity`, `toolGetStatus`, `toolGetPwmState`, `toolReadCurrents`, `toolReadAdc`, `toolGetServoState`) are handled in `servoWorker.js` but are **missing from `server.js`'s `BUS_WRITE_COMMANDS` table**. Effect: they reach the servo bus (via the queue, not immediately) but **do NOT require the control session**, unlike every other tool command. This looks intentional (telemetry shouldn't need exclusive control) but was never made explicit anywhere — flagging it here so it isn't "fixed" by accident later.

## 1. Control session

| Command | Description | Params | Response (success) | Response (error) | Wrapper | Call sites |
|---|---|---|---|---|---|---|
| `takeControl` | Requests exclusive control of the arm for this client, so it's allowed to issue movement/bus-write commands. Takes over from whoever currently holds it if `force` is set or nobody's locked it. | `force?:bool`, `password?:string` (to override a lock), `hostname?:string`, `label?:string` (default `'client'`) | `{type:'controlStatus', hasControl, youHaveControl, hasHolder, holder, holderHostname, holderIp, holderLabel, locked, lockedUntil}` | same shape + `message` | `takeControl(label, force, password)` | app.js × 4 (2381, 2394, 2856, 4142) |
| `releaseControl` | Voluntarily gives up the control session so another client can take it. | none | `controlStatus` payload | — | `releaseControl()` | app.js × 1 (2977) |
| `lockControl` | Takes control and locks it exclusively (password-gated) so no other client can take over — not even with `force` — until unlocked or the lock duration expires. | `password:string` (must equal server's control-lock password), `durationMs?:number` (default 15 min, capped 60 min), `hostname?`, `label?` | `controlStatus` payload + `ok:true` | `{type:'lockControlResult', ok:false, message}` | `lockControl(password, durationMs, label)` | app.js × 1 (2891) |
| `unlockControl` | Removes an active control lock, restoring normal take-control behavior for everyone. | `password?:string` (not required if caller already holds control) | `controlStatus` payload + `ok:true` | `{type:'unlockControlResult', ok:false, message:'Incorrect password'}` | `unlockControl(password)` | app.js × 1 (2914) |
| `getControlStatus` | Reports who currently holds the control session and whether it's locked. | none | `controlStatus` payload | — | `getControlStatus()` | app.js × 1 (2936) — rarely needed since the server also pushes `controlStatus` unsolicited on connect and on every change |

**Note:** `moveJoint`, `setServo`/`setServoAngle`, `setAcceleration` additionally reset the 5-minute control-idle-release timer on every call; other bus-write commands don't.

## 2. Status & diagnostics

| Command | Description | Params | Response | Wrapper | Call sites |
|---|---|---|---|---|---|
| `getStatus` | Returns the latest cached status (angle, position, speed, load, voltage, temperature, torque state) for every joint. Answered from cache — never touches the bus itself. | none | `{type:'status', joints:[...], cacheAgeMs}` | `getStatus()` (Promise) / `requestStatus()` (fire-and-forget) | `getStatus()`: app.js × 11, positionsManager.js × 1, blocklyRobotArm.js × 6 (template strings). `requestStatus()`: app.js × 4. Server also pushes `status` unsolicited every bus tick — most of the above are one-shot "read current angles right now" snapshots for move planning, not polling. |
| `getJointConfigs` | Reports which joint numbers (1–6) currently have a responding servo, so the UI knows which joints to render/enable. | none | `{type:'jointConfigs', count, total, joints:[{jointNumber, servoId, available}]}` | `requestJointConfigs()` (fire-and-forget) / `getJointConfigs()` (local cache getter, no WS round trip) | `requestJointConfigs()`: app.js × 2 (2423, 6987). `getJointConfigs()` cache read: app.js × 1 (7457). Server also pushes this unsolicited on connect and whenever the joint set changes. |
| `getServerDiagnostics` | Returns internal server/bus health counters — bus tick timing, write-queue depth, connected client count, uptime, build ID. | none | `{type:'serverDiagnostics', diagnostics:{...}}` | `getServerDiagnostics()` | app.js × 1 (2610) |
| `getEndTool` | Returns the cached identity/state of whatever end-tool is currently detected on the bus (ID 64). | none | `{type:'endTool', present, toolTypeId, known, tool, tools, lastProbeAt, lastError}` | *(no explicit wrapper — handled via the unsolicited `endTool` push)* | 0 explicit sends; app reacts passively via `applyEndToolState()` (app.js:920) |
| `refreshEndTool` | Asks the server to re-probe the end-tool node right now, instead of waiting for its automatic ~15s poll — used right after a tool swap. | none | `{type:'success', message:'End tool probe requested'}` (the actual updated tool state arrives as a separate unsolicited `endTool` push) | *(raw `sendCommand`)* | app.js × 1 (1079) |

## 3. Movement

| Command | Description | Type | Params | Response | Wrapper | Call sites |
|---|---|---|---|---|---|---|
| `moveJoint` | Commands a single joint to a target angle at a given speed — the core movement primitive nearly everything else builds on. | Immediate | `joint:number` (1-based), `angle:number` (deg), `speed?:number` (default 1500 step/s) | `{type:'success', message}` / `{type:'error', message, servoFault, joint}` | `moveJoint(joint, angle, speed)` (awaited) / `moveJointJog(joint, angle, speed)` (fire-and-forget, for jog buttons) | `moveJoint`: app.js × 21, blocklyRobotArm.js × 3 (templates). `moveJointJog`: app.js × 1 (3897) |
| `stopJoint` | Immediately disables torque (stops holding/moving) on one specific joint. | Immediate | `joint:number` | `{type:'success'}` / `{type:'error', message, joint}` | `stopJoint(joint)` | app.js × 1 (8134), blocklyRobotArm.js × 1 (template) |
| `stopAll` / `stopAllJoints` | Immediately disables torque on every joint at once — the emergency-stop command. | Immediate (aliases) | none | `{type:'success', message:'All servos stopped'}` / `{type:'error', message}` | `stopAllJoints()` — **always sends `stopAll`**, never the `stopAllJoints` string | app.js × 1 (3529, e-stop), blocklyRobotArm.js × 2 (975 real handler + 1 template). `stopAllJoints` (the raw string) has no electron-app call sites — reachable only by external clients |
| `setServo` / `setServoAngle` | Moves a joint to an angle using whatever speed was last set on that servo, rather than specifying speed per move. | Bus-write (queued) | `joint`, `angle` (uses servo's last-set speed) | `{type:'success'}` / `{type:'error'}` | `setServoAngle(joint, angle)` — sends `setServo` | 0 in app.js; blocklyRobotArm.js × 1 (template) — only reachable from Blockly-generated programs |
| `setSpeed` | Sets a joint's speed for use by subsequent moves that don't specify one explicitly. | Bus-write | `joint`, `speed` | `{type:'success'}` / `{type:'error', message, servoFault, joint}` | `setSpeed(joint, speed)` | **Dead** — 0 call sites (speed is set per-move via `moveJoint`'s `speed` param instead) |
| `setSpeedAll` | Sets the default speed for every joint at once. | Bus-write | `speed` | `{type:'success'}` / `{type:'error'}` | `setSpeedAll(speed)` | **Dead** — 0 call sites |
| `setAcceleration` | Sets a joint's acceleration profile (ramp-up/down rate), independent of its target speed. | Bus-write | `joint`, `acceleration` (0–254, clamped client-side, default 5) | `{type:'success'}` / `{type:'error'}` | `setAcceleration(joint, accel)` | app.js × 4 (3349, 3370, 5806, 5817), blocklyRobotArm.js × 2 (templates) |
| `setTorqueAll` | Enables or disables torque (holding power) on every joint simultaneously — used for the global "Torque On/Off" toggle. | Bus-write | `enabled?:bool` (default `true`) | `{type:'success'}` / `{type:'error'}` | `setTorqueAll(enabled)` | app.js × 1 (3781) |
| `rescanServos` | Re-probes every servo ID on the bus to detect newly connected or disconnected hardware, without restarting the server. | Bus-write (queued, NOT immediate) | none, rate-limited to 1 per 10s | `{type:'servoRescan', joints:[{joint, servoId, available, action}]}` — `action` ∈ `kept_existing \| rediscovered \| not_found` | `rescanServos()` | **Dead** — 0 call sites, not even in `index.html` |

**Removed:** `setJointCenter` (and the whole software joint-centering override — `servo-joint-centers.json`, `ServoController.setCenterPosition()`) was removed once EEPROM-based commissioning (Calibration tab, `writeServoEepromRaw` to the Position Correction register) made a software-only zero-point override redundant.

## 4. Commissioning / EEPROM (new — not in `API_DOCUMENTATION.md` at all)

| Command | Description | Params | Response | Wrapper | Call sites |
|---|---|---|---|---|---|
| `readServoEeprom` | Reads a servo's full commissioning profile — PID gains, overload/stall protection thresholds, hard angle limits, and max torque — directly from its onboard EEPROM. | `joint:number` | `{type:'servoEeprom', joint, profile}` — `profile` = PID gains + overload protection + angle limits + max torque | `readServoEeprom(joint)` | app.js × 1 (3420) |
| `writeServoEeprom` | Writes one or more EEPROM settings to a servo and persists them to `servo-pid-config.json`, so they're re-applied automatically the next time the server starts or if that servo is swapped for another unit. | `joint:number`, `values:object` — recognized groups: `{p,d,i,minStartupForce}`, `{overloadTorque,protTorque,protTimeMs}`, `{minAngleDeg,maxAngleDeg}` (together), `{maxTorque}` | `{type:'success', message, applied:[...]}` / `{type:'error', message:'No recognized fields in values'}` / `{type:'error', message, applied}` (partial progress) | `writeServoEeprom(joint, values)` | app.js × 1 (3480) |
| `commissionAllServos` | Applies every joint's saved EEPROM configuration to whichever physical servo currently responds at that joint ID in one pass — the "commission a freshly wired arm" button. | none | `{type:'servoCommission', results:[{joint, applied:[...], errors:[...]}]}` / `{type:'error', message:'No servo-pid-config.json found'}` | `commissionAllServos()` | app.js × 1 (3509) |

Each write is also persisted to `servo-pid-config.json` so it's re-applied automatically the next time the server starts (see the PID-tuning work earlier in this project).

## 5. Kinematics

All implemented by the `RobotKinematics` singleton in `kinematicsService.js`.

| Command | Description | Params | Response | Wrapper | Call sites |
|---|---|---|---|---|---|
| `kinematicsLoadURDF` | Loads a URDF robot description into the server's kinematics engine, defining joint geometry, limits, and tool offsets for all FK/IK calculations that follow. | `urdfXml:string` | `{type:'kinematicsLoaded', configured, jointCount, joints, urdfData, maxReachMm}` | `loadKinematicsURDF(urdfXml)` | app.js × 1 (7178) |
| `kinematicsForwardKinematics` | Computes the tool-tip XYZ position (and orientation) that a given set of joint angles produces. | `jointAngles:number[]` | `{type:'kinematicsForwardResult', result}` | `forwardKinematics(jointAngles)` | app.js × 3 (3946, 4957, 4958) |
| `kinematicsForwardKinematicsSteps` | Same as forward kinematics, but also returns each intermediate joint's position along the chain — used to draw the arm in the 3D view. | `jointAngles:number[]` | `{type:'kinematicsForwardStepsResult', result}` | `forwardKinematicsSteps(jointAngles)` | app.js × 1 (3997) |
| `kinematicsForwardKinematicsBatch` | Runs forward kinematics on a list of joint-angle sets in a single request, to avoid one round trip per pose. | `jointAnglesList:number[][]` | `{type:'kinematicsForwardBatchResult', positions}` | `forwardKinematicsBatch(list)` | app.js × 1 (4736) |
| `kinematicsInverseKinematics` | Computes joint angles that place the tool tip at a target XYZ (and optional orientation) — the core IK solve. | `targetPose:{x,y,z}`, `initialAngles?:number[]` | `{type:'kinematicsInverseResult', result}` | `inverseKinematics(targetPose, initialAngles)` | **0 in app.js** (built-in UI uses the local, in-process `kinematics.js` copy for lower latency — 11 call sites there instead). blocklyRobotArm.js × 2 (templates) — Blockly-generated programs go over the wire |
| `kinematicsRefineOrientationWithAccuracy` | Iteratively refines an existing joint solution to more precisely hit a desired tool orientation, trading extra compute for accuracy. | `targetPose`, `baseAngles`, `desiredOrientation`, `referenceAngles` | `{type:'kinematicsRefineOrientationResult', result}` | `refineOrientationWithAccuracy(...)` | **0 in app.js** (local copy used instead, 8 call sites). blocklyRobotArm.js × 2 (templates) |
| `kinematicsGetInfo` | Reports the currently loaded kinematics configuration — joint count, per-joint limits, and max reach. | none | `{type:'kinematicsInfo', configured, jointCount, joints, urdfData, maxReachMm}` | `getKinematicsInfo()` | **Dead** — 0 call sites |

**Why the built-in UI bypasses the server for IK/FK:** `electron-app/kinematics.js` is a synchronous, in-process mirror of the same algorithm — no network round trip, so the app's move planners use it directly. The WS versions exist for external API clients and for Blockly-generated programs (which run in the renderer but were written to call the server API, matching the public API surface external users see).

## 6. Linear Cartesian path

| Command | Description | Params | Response | Wrapper | Call sites |
|---|---|---|---|---|---|
| `executeLinearMove` | Drives the tool tip along a straight-line Cartesian path from its current position to a target, breaking it into small steps and interpolating joint moves along the way (rather than each joint moving independently in a curve). | `startAngles:number[]`, `targetPose:{x,y,z}`, `desiredOrientation?`, `stepMm?` (default 2.0), `speedMmPerSec?` (default 50) | Immediate ack `{type:'linearPathStarted', totalSteps, totalDistanceMm, intervalMs, requestId}`, then an **unsolicited** `{type:'linearPathComplete'}` later on the same connection | `executeLinearMove(...)` — wraps the two-part response in one Promise, plus its own 60s client-side timeout | app.js × 1 (4823) |
| `abortLinearPath` | Cancels an in-progress linear path move. | none | `{type:'success', message:'Linear path aborted'}` | `abortLinearPath()` — also sends `stopAll` as a belt-and-braces stop | **Dead** — 0 call sites |

Control-session enforcement for `executeLinearMove` is checked manually against `controlSession.ws` rather than through the generic bus-write gate, since it's technically an "instant" command that then drives the bus itself over time.

## Appendix C — Gaps vs. `API_DOCUMENTATION.md`

**Missing from the doc entirely:**
- Commissioning: `readServoEeprom`, `writeServoEeprom`, `commissionAllServos`
- The whole control-session family: `takeControl`, `releaseControl`, `lockControl`, `unlockControl`, `getControlStatus` — including which commands require it in the first place
- `getServerDiagnostics`
- Network/system: `getPiNetworkInfo`, `getPiEthernetSettings`, `setPiEthernetSettings`, `updatePiServerFromGit`
- All `kinematics*` commands
- `executeLinearMove`, `abortLinearPath`
- The six ungated tool-telemetry commands' control-session exemption (the commands themselves are documented, just not this behavior)

**Stale details in the existing doc:**
- `rescanServos`'s documented `action` values (`created`/`missing`/`lost`) don't match the actual code (`kept_existing`/`rediscovered`/`not_found`)
- `toolClearFaults`'s documented response message ("Tool faults clear command sent") differs slightly from the actual code ("Tool faults cleared")
- Status payload doc omits `readStale`, `pollError`, `lastGoodAt` fields that are actually present

**Nothing documented is phantom** — every command in `API_DOCUMENTATION.md` maps to something real; the issues are omissions and minor drift, not invented commands.
