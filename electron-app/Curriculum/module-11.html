Theory

What is Mechatronics?

Mechatronics is the engineering discipline that combines mechanical engineering, electrical engineering, and computer science into integrated systems. The word is a portmanteau of mechanics and electronics.

⚙️ Mechanical

Structure, joints, links, gears, bearings, materials

⚡ Electrical

Power supply, motors, wiring, PCBs, sensors

💻 Software

Control algorithms, interfaces, communication protocols

🎯 Control

Feedback loops, PID, path planning, safety limits

This arm is a complete mechatronic system. You cannot understand or fix a problem in one domain without understanding how it connects to the others.

Theory

The Full System Stack

Every action you trigger in the app travels through five distinct layers before a joint actually moves:

💻 HMI / Electron App — User clicks a button or runs a G-code file
↓ WebSocket (JSON, TCP 8080)
🔁 Network Transport — Command sent as a JSON packet over Wi-Fi or LAN
↓ Server on Raspberry Pi receives and parses
🆕 Controller (Raspberry Pi) — Motion planning, safety checks, PID setpoints calculated
↓ UART serial bus at 1 Mbaud
🔌 Serial Protocol — Position command sent to each ST3215 servo by ID
↓ Internal servo electronics
🔮 Actuator / Sensor — Motor drives joint; AS5600 encoder reads back position
Key insight: A fault at any layer produces a symptom at a different layer. A network drop (layer 2) looks like the arm ignoring commands (layer 5 symptom). Tracing faults means working through the stack systematically.
🏗️
Five-Layer System Stack
  1. HMI — Electron App: the user interface running on PC or the robot arm touchscreen
  2. WebSocket / JSON over TCP:8080: bi-directional real-time messaging
  3. Server on Raspberry Pi: control session management, kinematics solver, motion planning, safety enforcement, G-code/RAPID execution
  4. Serial bus interface (1 Mbps half-duplex): the daisy-chained physical link, polled every 20 ms
  5. ST3215 servo hardware + AS5600 sensors: actuators with internal PID, position/load/temperature sensors, and independent magnetic encoders via I²C
The LED strip and camera are peripheral subsystems alongside this stack — they do not carry motion commands. A fault at any one layer produces symptoms at a different layer; the key skill in this module is tracing a symptom back to its source layer.

💡
LED Strip — Cross-Layer Integration Example
The WS2812B LED status strip on the arm is a clean example of cross-layer integration. Its colour is determined by the server reading conditions across multiple layers simultaneously: the number of connected WebSocket clients (layer 2), the serial bus health (layer 4), joint thermal faults (layer 5), and whether a move is in progress (layer 3). A single physical output aggregates the state of the entire system. When diagnosing a fault, the LED strip gives you a fast first indicator of which layer to investigate.
🤏
End-Tool Node — Embedded Subsystem Integration
The ESP32 microcontroller at the tip of the arm (bus address 64) is a complete embedded subsystem on the same serial bus as the main joints. It has its own identity, fault register, PWM outputs, hobby servo drive, and ADC current sensing. Integrating it raised several engineering challenges:
  • Bus arbitration: two device types (servos and ESP32) share one bus — the server must address them correctly
  • Watchdog management: the ESP32 has its own communication watchdog that must be refreshed periodically
  • Fault isolation: an ESP32 fault must not freeze the main joint control loop
The end-tool controls (ping, fault clear, servo position, PWM duty) are in the Joint Control tab under the End Tool panel.
📷
Camera Subsystem — Perception Integration
A USB camera on the Raspberry Pi provides a perception input. It streams JPEG frames to port 8082, and the server proxies the ArUco marker detection and coloured block highlighting results into the WebSocket feed. From the app's perspective, vision data arrives alongside joint telemetry on the same connection. The Camera tab displays the live stream with overlaid detections. This is a genuine multi-process integration scenario: the control system and the vision system run independently and must be synchronised without blocking each other.
Worksheet

Activity — Full-System Trace

You will trace a single user action through all five layers of the system, observing what happens at each stage.

  • Open the app and connect to the arm via the Connection tab. Note the connection status — this confirms layers 1–2 are working.
  • Navigate to the 3D Visualization tab. This shows the forward kinematics model (layer 3/5 — the software model).

  • Click the Pop Out button in the 3D Visualisation tab to open the 3D model in a separate always-on-top window. Arrange this alongside the main app window showing Joint Control. Now, when you command Joint 1 to move 30°, you can simultaneously watch the 3D model update, the live angle readout change, and the load % respond — three data streams from three system layers, all in one view.

  • Open the Joint Control tab alongside. Command Joint 1 to move 30°. Simultaneously watch: (a) the 3D model update, (b) the live position readout, (c) the load value change mid-move.
  • Now use the G-Code Control tab to run a short two-move program. This exercises layers 1→5 with a programmatic sequence rather than manual input.
  • Use the Visual Programming (Blockly) tab to build the same two moves as a block program. Compare: which interface felt more reliable? Which was faster to create?
  • Finally, open the Kinematics tab. Enter the joint angles you used and confirm the displayed XYZ coordinates match where the arm physically ended up. This closes the loop between software model and physical reality.

Reflection Questions

So What?

Why Integration Is the Hard Part

Individual components — servos, Raspberry Pi, network — are well-understood in isolation. The difficulty in real engineering projects is making them work together reliably. This is why systems integration is a dedicated engineering role in industry.

When you built a Blockly program and watched it execute on the physical arm, you experienced the entire mechatronic stack in action. Most users never think about the five layers beneath a button press — but engineers must design, test, and maintain every one of them.

Industry connection: Automotive manufacturing robots, surgical robots, and warehouse automation systems all follow the same layered model — HMI → network/fieldbus → controller → actuator/sensor. The vocabulary and patterns you have learned here transfer directly.
