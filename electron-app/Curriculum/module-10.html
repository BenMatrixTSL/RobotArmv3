Data Logging & Diagnostics

Capturing, interpreting, and using live data from the robot arm to monitor health and diagnose faults.

🕔 60–75 min 🎯 Group: Intermediate 🔌 App tabs: Joint Control · Settings · Connection
Theory

Why Log Data?

A robot arm in operation generates a continuous stream of sensor data — joint positions, temperatures, supply voltages, and load readings. Capturing this data over time is called data logging. Engineers use logged data to:

📈 Trend Analysis

Spot gradual drift or degradation before failure occurs.

🔎 Fault Diagnosis

Replay events leading up to a fault to find the root cause.

✅ Performance Verification

Confirm the arm meets speed and accuracy specifications.

In safety-critical systems (ISO 10218), logs are a legal requirement — they prove the system operated within defined limits.

Theory

What Data Does a Servo Report?

The ST3215 servos used in this arm report several parameters over the serial bus. The app reads these and displays them in real time:

ParameterUnitsWhat it tells you
Positiondegrees (°)Current joint angle — compare to commanded angle to check accuracy
VelocityrpmHow fast the joint is moving — high values near limits risk overshoot
Load% of stall torqueMechanical load on the motor — sustained high load = overheating risk
VoltageVSupply rail health — drop under load indicates wiring or PSU issues
Temperature°CMotor winding temperature — above ~70 °C the servo will self-limit
Key point: Load is a proxy for current. Since torque = Kt × I, high load% means high current, which means high heat. Monitoring load is the earliest warning of an overload condition.

Connection Tab — Server Diagnostics Panel
The Connection tab includes a server bus diagnostics panel that shows: serial bus health, number of connected WebSocket clients, server uptime, and build ID. Use this alongside the Joint Control telemetry during diagnostics — the diagnostics panel gives you the infrastructure view (is the bus healthy? how many clients are connected?) while Joint Control gives you the sensor view (what are the joints doing?). Both together give a complete diagnostic picture.
Theory

Diagnostic Thinking: Symptoms → Causes

Good diagnostics follow a structured process — not guesswork. A common framework is Symptom → Hypothesis → Test → Conclusion.

SymptomPossible causesTest
Joint overshoots targetSpeed too high, PID gains wrongReduce speed, observe position trace
Temperature rising fastSustained high load, poor ventilationCheck load %, reduce payload
Voltage drops under movePSU current-limited, thin wiringMeasure V at servo headers during move
Position error accumulatesBacklash, encoder slippingCommand same pose 10×, log final position
WebSocket disconnectsNetwork jitter, Pi overloadedCheck Pi CPU usage, ping latency
🌡️
Thermal Fault
Symptom: LED strip flashing orange; one joint becomes unresponsive.
Cause: A servo has exceeded its safe operating temperature. The server automatically enforces a 30-second cool-down period for that joint.
Test: Check the Temperature (°C) field on the affected joint's card in Joint Control.
Resolution: Wait 30 seconds. Reduce duty cycle, speed, or payload for that joint. If it recurs, check for mechanical binding.
🔴
Serial Bus Loss / Server Recovery
Symptom: LED strip pulsing red; all joints frozen; Joint Control shows stale data.
Cause: The server lost contact with the serial bus (cable fault, power interruption, or hardware error). It is attempting to reconnect automatically with exponential backoff (waits 2 s → 4 s → 8 s → max 30 s between attempts).
Test: Check the Connection tab diagnostics panel for bus health status.
Resolution: Wait up to 30 seconds for auto-recovery. If it does not recover, check the serial bus cable connections and cycle the Pi's power.

Activity — Live Data Monitoring

You will observe live servo telemetry while the arm performs a repeating motion, and record what you see.

  • Connect to the arm using the Connection tab. Confirm the status indicator is green.
  • Open the Joint Control tab. Note the servo status panel — locate the live position, load, voltage and temperature readouts for each joint.
  • With the arm at its home/zero position, record the idle readings in the table below.
  • Command Joint 2 (shoulder) to move slowly between 0° and 60°, repeatedly. Observe how the load value changes at the extremes of the motion.
  • Now hold the end-effector gently (add a small manual load) and observe load % again. Record the difference.
  • Check the temperature reading before and after 5 minutes of continuous motion. Is it rising?
  • Open the Settings tab and locate any configurable temperature or load alarm thresholds. Note the default values.

Joint Control Tab — Confirmed Layout
The Joint Control tab shows six joint status cards (one per joint). Each card displays live data updated approximately every 20 ms from the servo bus:
  • Angle (°) — current joint position
  • Velocity — current speed
  • Load (%) — current draw as a percentage of stall torque
  • Voltage (V) — servo supply voltage
  • Temperature (°C) — servo motor temperature
Note: the Settings tab does not have alarm threshold sliders for temperature or load — the configurable value is the status watchdog interval (the fallback poll period if the server stops pushing). The servos have hardware thermal protection built in.
So What?

Why Does This Matter in Industry?

Industrial robots in factories run 24/7. A sudden failure mid-cycle can damage tooling, injure workers, or halt an entire production line. Predictive maintenance uses logged data — temperature trends, vibration signatures, load drift — to schedule servicing before failure, not after.

The techniques you practised here (monitoring load, watching temperature, noting voltage sag) are the same principles behind industrial SCADA (Supervisory Control and Data Acquisition) systems, just at a smaller scale.

Think about: If you were deploying this arm in a school workshop that runs 6 hours a day, what logging strategy would you design? What thresholds would you alarm on?
