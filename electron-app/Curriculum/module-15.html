Technical Documentation

Writing clear, complete, and useful engineering documentation — circuit diagrams, annotated code, test records, and user guides.

🕔 75–90 min 🎯 Group: Project 🔌 Context: Your own robot arm project
Theory

Why Documentation Matters

An undocumented engineering project is only half-finished. Without documentation, a system cannot be safely maintained, repaired, or handed to someone else. In professional settings, missing documentation can be a legal liability.

🔨 Maintenance

A technician needs to fault-find two years later. Wiring diagrams and component lists save hours.

👥 Handover

When you leave a project, someone else must understand it. Documentation is the bridge.

⚖️ Compliance

Regulatory approvals (CE marking, ISO certification) require evidence — test records, risk assessments, drawings.

System Block Diagram — Required Components
A complete system block diagram for this arm must include ALL of the following, with the communication protocol labelled at each boundary:
  • Electron App (PC/laptop) → WebSocket / JSON TCP:8080 → Server on Raspberry Pi
  • Server → UART serial bus (1 Mbps) → ST3215 Servos ×6
  • Server → Serial bus → ESP32 End-Tool Node (gripper/pump/ADC)
  • Server → LED Status Strip (peripheral output, WS2812B)
  • USB Camera → Server → WebSocket (vision results proxied to app)
  • AS5600 Magnetic Encoders → I²C bus → Raspberry Pi GPIO
Students who correctly draw all subsystems and label all protocol boundaries have demonstrated genuine understanding of the system architecture. Students who only draw "PC → Raspberry Pi → Arm" have missed critical subsystems.
Theory

What Makes Good Documentation?

Good documentation is not about length — it is about clarity and completeness for the intended audience. Key principles:

🎯 Audience-appropriate

A user guide for students uses different language than a maintenance manual for technicians.

📈 Evidence-based

Test records include actual measurements, not just "it worked". Show the data.

📅 Version-controlled

Date every document. Include a revision history so readers know which version is current.

📸 Visual where possible

A labelled photo, circuit diagram, or flowchart often communicates faster than paragraphs of text.

Example: Test Record Entry

Test Record — Robot Arm Project
Author: [Name] | Date: [Date] | Firmware version: 1.2.3
Test ID: T03 — Repeat Position Accuracy Specification: Joint 2 shall return to 45° within ±2° after 10 consecutive cycles.
Method: Commanded J2 to 45° × 10 cycles. Read position from Joint Control tab after each.
Results: 44.8°, 45.1°, 44.9°, 45.0°, 45.2°, 44.7°, 45.1°, 45.0°, 44.9°, 45.1°
Max deviation: 0.3° | Pass/Fail: PASS
Notice: The test record references the specification point, states the method, shows actual numbers, and gives an explicit pass/fail. A future engineer can reproduce the test and verify the result.
📋
Test Records — Specific Data Sources for This Arm
When writing test records, always cite the specific data source in the app:
  • Joint temperature: read from the Temperature (°C) field in the Joint Control tab — not estimated
  • Joint position / repeatability: read from the Angle (°) field in Joint Control — record 10 consecutive readings
  • Load (%): read from the Load field in Joint Control at three different poses
  • Cycle time: measure with a stopwatch, or compare the execution log timestamps in the G-Code Control tab
  • Connection time: time from pressing Connect to "you have control" in the Connection tab diagnostics
Results must show the actual measured value, the specification threshold, and a clear pass/fail verdict. "Temperature stayed acceptable" is not a test record — "Temperature peaked at 43°C against a 50°C threshold — PASS" is.
Worksheet

Activity — Document Your Project

Produce a documentation pack for your robot arm project. Use the checklist below to ensure nothing is missing.

  • Block diagram: Draw a system block diagram showing all hardware components (Pi, servos, sensors, PSU, app) and how they connect. Label each connection with the protocol used (UART, WebSocket, I²C, etc.).
  • Annotated program: Take your G-code or Blockly program from Module 12 and add annotations explaining each section — what it does and why (not line-by-line, just the important parts).
  • Test record: Design three tests against your specification points (from Module 14). Run each test, record actual results, and state pass/fail against the specification.
  • User guide: Write a one-page user guide for operating your arm program. Assume the reader has never used the app. Include: how to connect, how to run the program, what to do if it does not work, how to shut down safely.
  • Revision log: Add a short revision history table to each document: date, version number, and what changed.
🤖
RAPID as an Alternative to G-Code for Annotated Code
For the "annotated code" document, you may use a RAPID script from the RAPID tab instead of G-code. RAPID is closer to real industrial robot programming languages and produces a stronger portfolio artefact. The annotation requirement is the same: each MoveJ, MoveLXYZ, or GripperClose line must be commented with the physical action it performs, the reason for the speed choice, and any safety consideration. A well-annotated RAPID program demonstrates professional programming practice.

So What?

Documentation as a Professional Skill

In a survey of engineering employers, poor written communication consistently ranks in the top three skill gaps in new graduates. The ability to document a system clearly — so that someone else can understand, operate, and maintain it — is as valuable as the ability to build it.

The documentation pack you produce in this module is direct evidence of your engineering process. An assessor marking your project can tell, from your test records alone, whether you actually tested the system or just claimed it worked.

Think about: Could a student who was not in your class pick up your documentation pack and successfully operate your arm program? If not, what is missing?
